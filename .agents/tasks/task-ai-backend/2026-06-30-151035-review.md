# Python AI backend for SNBP admission predictor

This change adds a complete Python/FastAPI backend to an existing PHP web application (LangkahKampus). The backend provides an XGBoost ML model for SNBP university admission probability prediction, a recommendation engine for alternative programs, and an LLM-powered advisor chatbot using Fireworks AI. The PHP frontend is modified to call the Python backend first, falling back to its existing deterministic formula when the backend is unavailable. Docker Compose orchestrates the three-service topology (PHP, Python, MySQL).

**Watch for:** The ML model is trained on synthetic data generated from the deterministic formula itself, so it cannot outperform the formula on real-world inputs (confirmed). The SIDATA SQL file is not mounted into the ai-backend container, meaning SIDATA will fail to load at runtime (confirmed). CORS is configured as `allow_origins=["*"]` with credentials enabled, which browsers will reject and which represents an open access posture (confirmed).

## High-level view

The prediction model is an XGBoost regressor trained on ~30,000 synthetic samples derived by running the existing PHP formula with added noise and interaction terms. Because the training signal is the formula plus minor perturbations, the model approximates the formula rather than learning from real admission outcomes. The R2=0.9457 metric reflects how well it reproduces the formula, not how well it predicts actual admissions.

The system architecture is a sidecar pattern: PHP proxies requests to the Python backend via internal Docker networking (`http://ai-backend:8000`). The PHP layer adds admission history and peer-count data from MySQL. If the Python service is down, the PHP layer falls back to its original deterministic calculation. Timeouts are 3s connect / 5s total.

The SIDATA loading mechanism parses `database/seed_sidata.sql` via regex at startup, building an in-memory store of ~3,058 programs. However, the Dockerfile copies only `app/` and `models/` into the container — the SQL file lives outside `ai_backend/` and is never mounted. The container will start with zero programs loaded, producing fallback predictions for every request.

The LLM advisor wraps Fireworks AI with a system prompt in Indonesian, proxied through PHP. When no API key is configured, a hardcoded fallback provides generic advice based on the probability tier. The `/api/advisor` endpoint is exposed without auth on port 8000, meaning external clients can call Fireworks AI (billed per token) directly.

<details>
<summary>Issues (6)</summary>

1. **Circular training signal** — The XGBoost model is trained on synthetic data generated by the deterministic formula plus noise. It cannot improve prediction quality beyond the formula. Train on real admission outcomes or clearly document this as a smoothed approximation.
2. **SIDATA SQL not available in container** — The Dockerfile does not COPY or mount `database/seed_sidata.sql`. At runtime, `SIDATAStore.load()` will warn and load zero programs, making all predictions use fallback defaults. Add a volume mount in docker-compose or COPY the file during build.
3. **CORS `*` with credentials** — `allow_origins=["*"]` combined with `allow_credentials=True` is rejected by browsers per the CORS spec. Either restrict origins to the PHP frontend's origin or drop `allow_credentials`.
4. **No authentication on Python endpoints** — The Python backend is exposed on port 8000 and accepts requests from any origin with no auth. Anyone who can reach the host can call `/api/predict` and `/api/advisor` directly, bypassing PHP and running up Fireworks API costs.
5. **Advisor prompt injection** — User messages are placed directly into the LLM messages array with no sanitization. A user could instruct the model to ignore its system prompt.
6. **Score values not validated as numeric** — `scores` is typed `Dict[str, Any]` and the endpoint calls `float(score)` without validation. Non-numeric values produce an unhandled 500 instead of a 422.

## Synthetic training data produces a circular model

The training pipeline (`prepare_data.py`) generates 10 synthetic students per program (30,580 total) by sampling random scores, running the same 6-variable weighted formula that already exists in PHP, and adding Gaussian noise (sigma=0.03) plus three small interaction terms. `train_model.py` then fits an XGBoost regressor against this synthetic target.

The resulting model can only learn to reproduce the formula. The reported R2 of 0.9457 measures agreement with the formula, not predictive power against real admission data. The three interaction terms (score-ranking bonus, competition-accreditation penalty, top-10% bonus) are the only signal that differentiates the model from a direct formula call, and they sum to at most ~0.05 probability units. The model will never disagree meaningfully with the deterministic fallback.

## SIDATA file missing from container build context

`config.py` computes `SIDATA_SQL_PATH` relative to the project root:

```python
SIDATA_SQL_PATH: str = os.path.join(
    os.path.dirname(os.path.dirname(os.path.dirname(os.path.abspath(__file__)))),
    "database",
    "seed_sidata.sql",
)
```

Inside the container, this resolves to `/database/seed_sidata.sql` (one level above `/app`). The Dockerfile only copies `app/` and `models/`. The `docker-compose.yml` mounts the SQL file into the MySQL container's init directory but not into `ai-backend`. The container will log "WARNING: SIDATA SQL file not found", load zero programs, and every prediction will use hardcoded defaults (`competition_ratio=15.0`, `daya_tampung=50`).

Fix: add `- ./database/seed_sidata.sql:/database/seed_sidata.sql:ro` to the `ai-backend` service volumes, or COPY it during build.

## CORS misconfiguration

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.CORS_ORIGINS,  # ["*"]
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

The CORS specification forbids `Access-Control-Allow-Origin: *` when credentials are included. Browsers will block credentialed responses. The PHP frontend uses server-side cURL so it's unaffected, but if the frontend ever makes direct XHR calls to the Python backend (or if a developer tests from a browser), they'll fail silently.

## No auth, no rate limiting on exposed endpoints

The Python backend is published on `ports: "8000:8000"` in docker-compose, accessible on the host network. There is no authentication, no API key, no rate limiting. The `/api/advisor` endpoint calls Fireworks AI (billed per token). Any external client can hit this endpoint directly and run up costs.

Fix: remove the `ports` mapping (keep it internal on `langkahkampus-net` only), or add a shared secret header that PHP sends and Python validates.

## Score computation accepts arbitrary structures

The `scores` field in `PredictionRequest` is typed as `Dict[str, Any]`. The endpoint iterates over it handling both nested `{subject: {semester: score}}` and flat `{subject: score}` formats, calling `float(score)` directly. A malformed request like `{"Math": {"s1": "abc"}}` will raise a `ValueError` and produce an unhandled 500 error rather than a 422 validation error. A Pydantic custom validator or a try/except with `HTTPException(422)` would be cleaner.
