# Python AI backend for SNBP admission predictor (v2)

This change adds a Python/FastAPI AI backend to a PHP web application (LangkahKampus) providing ML-based SNBP admission probability prediction, program recommendations, and an LLM-powered advisor chatbot. The v2 pass addresses six issues from the first review: SIDATA SQL is now COPY'd into the container and volume-mounted, CORS credentials are disabled, the ai-backend port mapping is removed (internal-only access), score parsing returns 422 on invalid input, the training script documents its synthetic-data limitation, and a `_sanitize_message()` function filters basic injection patterns.

**Watch for:** The injection filter is trivially bypassable by paraphrasing or using non-English phrasing, and there are no tests covering the sanitization logic (confirmed). The `context` dict passed to the advisor is not validated or size-limited, providing an alternative injection surface (confirmed). The `scores` field remains typed `Dict[str, Any]` with no Pydantic-level validation, so the 422 error format doesn't match Pydantic's standard validation response shape (confirmed).

## High-level view

The SIDATA container fix, CORS correction, and network isolation removal all properly resolve their respective v1 issues. 34 tests pass.

The prompt injection mitigation uses regex filtering against six English-language patterns and a 2000-character truncation. This stops the most naive attacks but is bypassable by rewording, using Indonesian, or using unicode tricks. More importantly, the `context` dict from the request body is serialized directly into a system message without sanitization or size constraint, providing an alternative injection channel that bypasses the new filter entirely.

Score validation catches `ValueError`/`TypeError` and raises `HTTPException(422)`, preventing unhandled 500s. Because validation happens in application code rather than the Pydantic schema, the error format differs from Pydantic's standard 422 responses, which could confuse API consumers expecting a uniform error structure.

<summary>Issues (4)</summary>

1. **Sanitization has no test coverage** — `_sanitize_message()` is untested. Add unit tests for truncation behavior, each regex pattern, and bypass cases to prevent regressions.
2. **Context dict is an unsanitized injection vector** — `request.context` is serialized into a system message (`"Data prediksi siswa:..."`) without size limits or content filtering. A caller can inject arbitrary text via `context["input_summary"]["target_program"]` or other string fields.
3. **422 error format inconsistency** — The manually raised `HTTPException(422)` returns `{"detail": "..."}` (a string), while Pydantic validation errors return `{"detail": [...]}` (a list of objects). Consumers must handle both shapes.
4. **Injection filter is English-only, trivially bypassable** — The six regex patterns only match English phrases. Since the system prompt and user base are Indonesian, injection attempts in Indonesian (or paraphrased English) pass through unfiltered.

## Sanitization coverage gap

The `_sanitize_message()` function was added in response to the v1 prompt injection concern, but no test exercises it. The test suite covers advisor endpoint behavior (message returns reply, empty message returns 400) but never sends a message matching `INJECTION_PATTERNS` or exceeding `MAX_MESSAGE_LENGTH`. Without tests, future refactors could silently remove or break the filter. A minimal test set would verify: (1) messages over 2000 chars are truncated, (2) each pattern in `INJECTION_PATTERNS` is replaced with `[filtered]`, (3) the function returns stripped output.

## Context dict as injection surface

The `AdvisorRequest.context` field is `Optional[Dict[str, Any]]` — completely unvalidated. In `get_advisor_response`, context values are interpolated into a system-role message:

```python
if "input_summary" in context:
    summary = context["input_summary"]
    if "target_program" in summary:
        context_msg += f"\nProgram target: {summary['target_program']}"
```

A malicious caller can set `context["input_summary"]["target_program"]` to a multi-line string containing override instructions. Because this lands in a `system` message (not `user`), it sits adjacent to the system prompt and carries higher weight in most LLMs. The sanitization function is only applied to `message`, not to context-derived content.

Fix: either validate context fields against expected types and lengths (program name < 200 chars, probability is numeric, etc.) or run `_sanitize_message()` over the assembled `context_msg` before inserting it into the messages array.

## Error format divergence on invalid scores

When a non-numeric score triggers the `except (ValueError, TypeError)` block, the endpoint raises:

```python
raise HTTPException(
    status_code=422,
    detail=f"Invalid score value: all scores must be numeric. Error: {str(e)}",
)
```

This produces `{"detail": "Invalid score value: ..."}`. But when Pydantic itself rejects a request (e.g., `school_ranking` is a string), FastAPI returns:

```json
{"detail": [{"loc": ["body", "school_ranking"], "msg": "...", "type": "type_error.integer"}]}
```

A frontend handling 422 responses must now check whether `detail` is a string or a list. Using a `@validator` on the `scores` field in `PredictionRequest` would produce a consistent error shape.
