# Phase 5 Enhancement & Submission Polish

This change adds five presentation-oriented features for hackathon submission: an AMD GPU training script with ROCm detection, model evaluation chart generation, multi-turn conversation history in the AI advisor, two new AMD-branded landing page sections, and an end-to-end demo script with mock mode. The multi-turn advisor is the only piece that modifies production code paths; the rest are additive scripts and static content.

**Watch for:** The conversation history limit is enforced independently at three layers (JS, Python schema, Python service) with inconsistent caps—20 messages client-side vs 10 entries server-side—and the server takes the *first* 10 entries, discarding recent context (confirmed). The `conversationHistory` array never resets when a new prediction is made, so stale context from a prior session bleeds into subsequent advisor conversations (confirmed). The visualization script evaluates on the full training set, overstating model accuracy in the generated charts (confirmed).

## High-level view

The multi-turn advisor threading flows from JavaScript through PHP to FastAPI with sanitization at the service layer. The prompt is assembled in correct message order (system, context, history, current user message). The critical gap is that the server-side truncation takes `history[:10]` (the *oldest* entries) while the client sends the *last* 20 messages, meaning the backend silently discards the most recent context—exactly the opposite of what's useful.

The landing page additions are inline-styled HTML sections. The AMD sections won't inherit future theme changes made to the shared stylesheet, but for a hackathon deadline this is pragmatic.

The demo script operates in mock and live modes with self-contained hardcoded responses. The visualization script generates four presentation charts but evaluates predictions against the same data the model was trained on, so the reported metrics are in-sample accuracy rather than generalization performance.

<summary>Issues (5)</summary>

1. **Server truncates oldest history, discards newest** — `history[:MAX_HISTORY_ENTRIES]` takes the first 10 items from the array. The client sends the *last* 20 messages via `.slice(-20)`. After 5+ exchanges, the server keeps only the oldest context and drops the recent turns. Change to `history[-MAX_HISTORY_ENTRIES:]` or align the cap with the client.

2. **No history reset on new prediction context** — `conversationHistory` is a module-global that never resets. If a user runs a new prediction and returns to the advisor, stale conversation history from the previous prediction is still attached, potentially confusing the LLM with contradictory context. Reset the array when `predictionContext` changes.

3. **Client/server limit semantic mismatch** — JavaScript enforces 20 *messages* (comment says "10 exchanges"); Python enforces 10 *entries*. These should use the same unit and the same number.

4. **`subprocess.run` in ROCm detection without absolute path** — `rocm-smi` is resolved via PATH. In a production deployment the full path (`/opt/rocm/bin/rocm-smi`) would be preferable to avoid PATH-based execution of unintended binaries. Low practical risk for a hackathon.

5. **Visualization evaluates on full training set** — `visualize_evaluation.py` runs predictions on the entire dataset including training samples. The charts and metrics (R2, MAE in the title) overstate real-world accuracy. Consider using a held-out test split.

## Client/server history cap mismatch

The JavaScript comment says "max 10 exchanges" and enforces 20 messages (10 user + 10 assistant) via `.slice(-20)`. The Python service constant is `MAX_HISTORY_ENTRIES = 10`, and it slices `history[:MAX_HISTORY_ENTRIES]`—taking the first 10 *items* from the list, regardless of role.

The mismatch means the backend silently drops the most recent history entries (since it takes the *first* 10, not the *last* 10). Combined with the client sending the *last* 20 messages, the server keeps only the oldest 10 of those. Recent context is more valuable than stale context, so this truncation is backwards:

```python
# Current: keeps oldest entries
for entry in history[:MAX_HISTORY_ENTRIES]:

# Should be: keeps newest entries
for entry in history[-MAX_HISTORY_ENTRIES:]:
```

## No conversation reset across predictions

`conversationHistory` in `advisor.js` is declared at module scope and never cleared. The prediction context comes from `sessionStorage.getItem('lastPrediction')` and updates when a new prediction is made, but the history array still contains exchanges referencing the *old* prediction's probability and variables. The LLM will see contradictory signals: the system context says "probability 45%" while history messages discuss "your 72% chance."

A natural reset point would be when `predictionContext` differs from the last value used.

## Visualization on training data

```python
X = df[FEATURE_COLS].values
y = df[TARGET_COL].values
y_pred = np.clip(model.predict(X), 0.05, 0.95)
```

The model was trained on this data (or an 80% subset per `train_on_amd_cloud.py`'s `test_size=0.2` split). The resulting scatter plot and R2/MAE figures represent in-sample fit. For the hackathon slides this may be a deliberate choice (better-looking numbers), but the charts should ideally be labeled as training-set evaluation or regenerated on the held-out 20%.

## ROCm detection subprocess

```python
result = subprocess.run(
    ["rocm-smi", "--showid"],
    capture_output=True,
    text=True,
    timeout=10,
)
```

The 10-second timeout prevents hangs. In a production deployment, using the absolute path `/opt/rocm/bin/rocm-smi` (which the script already checks for via `os.path.exists("/opt/rocm")`) would tighten the execution surface.
